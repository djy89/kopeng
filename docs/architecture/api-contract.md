# API Contract

> Extracted verbatim from CLAUDE.md (2026-09-07).

### API Contract

All responses use envelope `{ data: T, meta?: { ... } }`. Input validation via Zod schemas in `src/api/routes.ts`. Rate-limited via `@fastify/rate-limit`.

`GET /api/memories` supports `fields=lite`: the embedding column is omitted (returned as `null`) and `limit` may go up to 1000/page; `fields=full` (default) keeps the old shape with `limit` clamped to `config.search.maxLimit` (100). Tag lookup is batched (one `ANY($1)` query per page, not per-row). Lite is for list consumers that never read vectors — the viz graph is the primary caller.

**PUT `/api/memories/:id` snapshots on EVERY effective mutation (Phase 2 — F3/T22 covered confidence only).** The handler computes whether content, type, scope (post-canonicalization), metadata, tags, or `is_locked` actually changed (plus the pre-existing confidence check) and snapshots via `dreamStore.snapshotRevision(memoryId)` iff any did; a byte-identical PUT (resending the current values) snapshots nothing. These revisions carry `created_by_dream_id = NULL` — revision-only reversibility, no `dream_audit_log` row (ruling 4; same posture as T30.3 crystallization). Known accepted quirk: the metadata comparison is on the serialized JSON string, so a semantically-equal but key-reordered metadata patch still snapshots — an extra revision, never a lost one. `memory_revisions` now snapshots the whole row, not just content/embedding/tags/confidence: `scope`, `type`, `updated_at`, `last_seen` (SQLite migration v8, PG v10) and **`is_locked` (SQLite v10, PG v12)** — all plain additive `ADD COLUMN`, no CHECK touched. `restoreRevision` `COALESCE`s the four restorable columns (`scope`, `type`, `last_seen`, `is_locked`) against the live row, so a legacy (pre-v8 / pre-v10-PG for the first three, pre-v10-SQLite / pre-v12-PG for the lock) NULL revision never clobbers live values; `updated_at` is recorded on the snapshot for forensics but NOT restored — restore always stamps its own `updated_at = now()`, since a restore is itself a correction happening now.

**Why `is_locked` had to join the snapshot (WS0).** `is_locked` is THE Hard Anchor — it is what stops promotion, the dream `decay` tier and maintenance §2 from archiving a row — and it is **model-writable**: the MCP `update_memory {locked}` argument forwards to `body.is_locked` on the PUT. Until this change the `memory_revisions` INSERT column list omitted it on BOTH backends, so a model-issued `{locked:false}` was **unrecoverable and unrecorded** (no revision captured the prior lock, no `dream_audit_log` row named the change) and the row became archivable on the very next promotion/dream pass — while the README claimed every write was reversible. Two consequences worth knowing: (1) the column is deliberately **NULLABLE with no default** on both backends — a `DEFAULT 0`/`DEFAULT FALSE` would backfill every pre-migration revision on the live corpus with "was unlocked", and the restore `COALESCE` would then *strip* real anchors on rollback; (2) full-row restore cuts both ways — rolling back to a revision snapshotted while the row was UNLOCKED will clear a lock applied afterwards, exactly as it already reverts a later scope/type change. That is bounded: rollback is admin-gated, explicit, and itself reversible, since `restoreRevision`'s pre-rollback snapshot captures the live lock. **Deliberately NOT audited:** no new `dream_audit_log` change class was added. An operator PUT has no dream row to hang an audit entry off (the FK is `NOT NULL`), so auditing lock toggles would mean minting a carrier dream per toggle; and extending the `change_class` CHECK costs a full table rebuild on SQLite and a validating `DROP`/`ADD CONSTRAINT` against the live PG corpus. Per ruling 4 the revision snapshot IS the reversibility record for the operator-edit class. Pinned by `tests/unit/revision-lock-reversibility.test.ts` (SQLite, incl. the legacy-NULL guard) and the PG twin in `tests/integration/pg-executed-sql.test.ts`. The lock is also on the READ surface: `MemoryRevision.is_locked` is `boolean | null` (both mappers normalize — SQLite stores 0/1, PG stores BOOLEAN — so the revision shape has one spelling; `null` means "predates the column" and stays distinguishable from `false`), served by the admin-gated `GET /api/memories/:id/revisions`. **One write path, not two (WS0):** `IDreamStore.setMemoryLock` is a DEPRECATED second name for `IMemoryStore.updateLocked` — it had already drifted (it skipped `updated_at`) — and both backend implementations now FORWARD to the canonical method rather than re-spelling the SQL, so there is exactly one implementation of "write `is_locked`" per backend. It is retained only because it is an exported store method with possible out-of-repo callers; there is no in-repo production caller, and new code should call `updateLocked`. The forwarding is asserted, not trusted: `tests/unit/dream-queries.test.ts` writes one memory by each path and requires byte-identical whole-row state (including `updated_at`, the column the drift lost), with the PG twin in the executed-SQL suite.

**Revision retention + redaction (team-review #22 S1).** Revisions serve PRE-EDIT content verbatim, so the surface is governed: (1) `GET /api/memories/:id/revisions` is **admin-gated** — a public read would defeat redaction (an operator PUT that scrubs a secret must not leave the old text readable by anyone on the port; no hook/MCP/viz consumer reads this over HTTP, so the public-reads contract is unaffected). (2) `snapshotRevision` **trims the operator-edit class** (`created_by_dream_id IS NULL`) to the newest `REVISION_KEEP_PER_MEMORY` (20) per memory on both backends; dream-linked revisions are NEVER auto-trimmed — they are the audit trail's reversibility record. (3) **Admin purge routes** are the deliberate excision path: `DELETE /api/memories/:id/revisions/:revision` (one revision; 404 if absent) and `DELETE /api/memories/:id/revisions` (whole history; returns the count). Purging a dream-linked revision forfeits that apply's rollback — an explicit admin trade; there is deliberately no bulk/unscoped variant. Store methods `deleteRevision`/`deleteRevisions` on `IDreamStore`, both backends.

**Operator-config `config` blob merge (T26):** `PATCH /api/operator-config` MERGES the provided `config` JSON object into the stored blob **server-side** instead of replacing it — killing the old client read-merge-write TOCTOU where a viz/MCP write could clobber an engine cursor write (`dream_window_cursor` / `dream_whole_corpus_cursor` live in the same blob). **Merge rule (shallow, top-level keys):** an explicit `null` value DELETES that key; any other value SETS it; keys absent from the patch are left untouched. Top-level columns (`timezone`, `idle_minutes`, `auto_accept_*`, `reasoner_provider`, …) keep their prior REPLACE semantics — only the `config` blob merges. The handler's read→merge→write is serialized by a per-app promise chain so two concurrent PATCHes to disjoint blob keys both persist. Clients send PARTIAL patches: `set_operator_config` (MCP) forwards a `config` object as-is (no read-merge-write); the viz whole-corpus toggle sends only `{ config: { dream_whole_corpus_cadence } }`. Note: the dream engine's own cursor `commit()` still writes through the store directly (`updateConfig` with a full re-read-and-merged blob) — that path is unchanged and merges by construction; the residual engine-vs-PATCH TOCTOU is pre-existing and out of T26's scope.

**Rejected alias entries are REPORTED, not swallowed (WS0).** A PATCH whose `config` names `scope_aliases` runs the RESULTING merged table through the shared `buildScopeResolution` and returns any skipped entries additively as `meta.alias_entries_rejected` (`{alias, canonical, reason}` each, plus one `logger.warn` per reject). Before this, such a PATCH returned a bare `200` while the resolver silently dropped the entry at load time — the exact-match write path kept ignoring it, recall never expanded the scope, and the rows stayed dark, with the operator believing the ruling took. **It reports; it does not refuse** — refusing would be a breaking change to an existing endpoint, and `POST /api/admin/scopes/rule` is already the validating path for alias entries (it rejects a would-be table that the resolver won't fully accept). A clean PATCH, or one that doesn't name `scope_aliases`, is byte-identical to before (no `meta`). Pinned by `tests/unit/operator-config-alias-rejects.test.ts`.

**Admin key (T27 2026-07-24; widened by sweep-3 PB-2 2026-07-27):** **every** mutating endpoint outside observation ingestion (which rides its own `OBSERVATION_API_KEY` — the two keys are set independently, so configuring only the admin key leaves the ingestion path open) requires `x-api-key: ADMIN_API_KEY` when that env var is set — core memory CRUD (`POST /api/memories`, `/batch`, `PUT`/`PATCH /api/memories/:id`, `POST /api/memories/:id/archive`), slots, `PUT`/`DELETE /api/context`, `POST`/`DELETE /api/artifacts`, `POST /api/memories/:id/graph`, plus the T27 operator set (`PATCH /api/operator-config`, dream trigger/resolve, rollback, admin promote/reindex/backup/discover/discovery-maintain). Unset = open dev mode, mirroring the `OBSERVATION_API_KEY` posture; deliberately a SEPARATE key — the observation key is distributed across hook configs on several machines and must not carry admin power.

T27 covered only the operator endpoints; core CRUD had **no auth handler at all**, so on the old wildcard `HOST` default a first run with no `.env` exposed full read *and write* to the network. That mattered more than an open read: an injected memory is recalled into a model's context on a later prompt and acted on — prompt injection with persistence. Because the gate is a no-op when no key is set, **the bind address is the real control**, which is why `config.server.host` now defaults to `127.0.0.1`.

**Reads stay public, including the POST-shaped ones** — `/api/memories/recall`, `/search`, `/surface`, `/traverse`. The recall hooks call those on every prompt with no key; gating them breaks recall for every client, silently (hooks fail closed to "no memories"). `tests/unit/core-crud-auth.test.ts` pins both halves: mutations 401 without/with a wrong key, reads never 401. **One deliberate exception:** `GET /api/memories/:id/revisions` is admin-gated (team-review #22 S1) — it serves pre-edit content, no hook depends on it, and leaving it public would make redaction-by-PUT ineffective.

Key plumbing: the viz proxy injects it server-side (env → repo `.env` fallback; the browser never holds it) for the routes on its `ADMIN_ROUTES` allowlist; the MCP stdio server does a non-overriding dotenv `.env` fallback, so the write tools (`store_memory`, `update_memory`, `archive_memory`, `set_context`, `store_artifact`, `trigger_discovery`) and `trigger_dream`/`resolve_dream`/`set_operator_config` need no per-client env plumbing; `npm run promote`, `sync:indexes`, `triage:anchors:live`, `run-discovery`, and the migration scripts send it from env too.

**Viz remote read-only (sweep-3 PB-3):** on a non-loopback bind without `VIZ_ALLOW_REMOTE_ADMIN=1`, `scripts/viz-server.js` refuses every non-GET method with 403 *at the proxy*. Withholding the admin key alone was never enough — the proxy forwards any method, and on a keyless default install nothing downstream would have stopped it. `isLoopbackHost`/`isReadOnlyBlocked` are exported pure functions behind an `isMain` listen guard so the policy is unit-tested (`tests/unit/viz-remote-readonly.test.ts`) rather than requiring a real remote bind.
