> Extracted verbatim from CLAUDE.md (2026-09-07).

### Static Surfacing (C1)

Enriches what the per-prompt hook injects — relevant tools, skills, and project conventions — from the operator's `~/.claude` indexes, served by a server-side endpoint, with a causal precision metric. Spec lives in the maintainer notes (not shipped). Status: all C1 tickets (T11–T16) landed on `sprint/20260620-c1`; **GATE C1 signed off 2026-07-24** (skill acceptance well clear of the bar, tool acceptance trending up, latency added p95 0.0ms; the operator's own acceptance rates stay in the maintainer notes, periodic re-check scheduled).

**Index sync importer (T11)** — `scripts/sync-claude-indexes.ts`, `npm run sync:indexes`. HTTP client (owns no `src/**`) that parses `~/.claude/{TOOLS_INDEX,SKILLS_INDEX,PROJECT_INDEX}.md` into KOPENG memories via the REST API. Scope mapping:

- Tools → `client:claude-tool` (existing scope)
- Skills → `client:claude-skill` (new)
- Per-project conventions (PROJECT_INDEX rows) → `project:<slug>` (new)
- `client:claude-convention` (global conventions) — RESERVED; no source file populates it today

All entries: `type: 'reference'`, confidence **0.55** (catalog-tier — won't outrank real project/global recall). Idempotent: content-hash dedup + external-key reconcile (changed description → update, not a new row). `--dry-run` (read-only) and `--prune` (archives orphaned index memories via `POST /api/memories/:id/archive`). NOTE: not yet run against the live server — that is a deferred operator step (running it writes catalog memories into the live DB). Tag schema: `['claude-index', '<tool|skill|convention>', 'source:<index-file>']`. Scheduled sync: WIRED via Windows Task Scheduler — `scripts/ops/install-sync-task.ps1` (elevated) registers a daily task running `scripts/ops/sync-indexes-task.ps1` (→ `npm run sync:indexes`) as the operator (S4U, never SYSTEM — it must read `~/.claude`). Runbook: `docs/ops/scheduled-sync.md`.

**Surfacing endpoint (T12)** — `POST /api/surface` (Zod-validated) + `src/surfacing/surface.ts`. Runs the stores IN-PROCESS (`IMemoryStore`/`IVectorSearch`), never self-HTTP (mirrors the dreaming runner's in-process rule). Per-scope RRF (semantic + FTS, K=60) over all four scopes; per-class score floor (~0.015, RRF scale) + caps **≤3 tools / ≤2 skills / ≤2 conventions** (defaults, overridable via `caps` in the request); cross-class dedup; fail-silent (empty on error). `searchScope` takes an `indexTag` (default `CLAUDE_INDEX_TAG`) so lanes filter to curated entries only. **Procedural-skill lane (thin Skills layer):** the `skill` class unions the `client:claude-skill` catalog lane (binding **hard**) with a second search over the request's `project:<name>` scope filtered by `SKILL_TAG` (binding **advisory** — auto-derived workflow memories, see the Skills track above); merged into the `skills` class (dedup by id, keep max score) under one cap, with per-id binding so catalog stays hard while procedural is advisory. Procedural skills are project-scoped only — no `projectScope` in the request ⇒ the procedural lane is skipped (no `global` producer exists, so surfacing never proposes arbitrary global memories that merely share the tag). **Phase 4 scope identity (T8):** `SurfaceDeps` gains optional `canonicalizeScope`/`expandScope` closures — the project lane's scope is canonicalized through the alias table and expanded to its alias group, and the request's declared anchor scopes (`scopes[]` in the schema, max 16 — the P4 marker cap) get the same treatment, so procedural skills and per-project conventions on either side of a scope migration stay reachable. Fail-open (absent closures ⇒ byte-identical pre-Phase-4 lanes; a closure failure degrades to the raw scope), catalog lanes (`client:claude-*`) untouched, procedural binding stays advisory. The route threading is pinned by probe 7 of `tests/integration/server-wiring.test.ts` (an alias-variant `project_scope` must surface the canonical-scope procedural skill).

Request: `{ prompt, cwd?/project_scope?, scopes?, caps? }`. Response: per-class arrays of `{ class, key, title, content, score, binding }` where **`binding: 'hard'`** for tools/skills and **`binding: 'advisory'`** for conventions — so the hook and the C0 act-or-explain rule can tell them apart.

**Recall-hook thin client (T16)** — `scripts/hooks/memory-prompt-search.mjs` now calls `/api/surface` inside its existing `Promise.all`. Recall keeps the 3s hard ceiling; `/api/surface` runs under its own tighter **2s leash** so a stalled surface call cannot drag a fast recall to 3s — fails to empty on timeout. Composes labelled blocks:

- "Tools that may help:" + "Skills that fit this task:" — **HARD** (C0 act-or-explain rule applies)
- "Project conventions (FYI):" — **ADVISORY** ("consider it")

Surface results are deduped against recall memories via `norm()`. Preserves both output shapes (`hookSpecificOutput.additionalContext` for Claude Code, `--codex` plain-text) and the `MIN_PROMPT_LEN` gate; fail-silent exit-0 throughout. **Phase 4 (T9):** the hook sends its P4 anchor-marker scopes in the surface body (`scopes[]`, omitted when empty — no marker ⇒ byte-identical request), and the T32 canonical-trigger cache refresh passes `expand=aliases` on its list call so trigger-term canonicals still stored under an alias variant stay in the index during a migration (an old server's non-strict query schema simply strips the unknown param — exact-match, the pre-Phase-4 behavior). `scripts/bench-recall-hook.ts` measures added latency over the C0 baseline (informational). Known: `client:claude-tool` is queried by both the legacy C0 tool-recall path and `/api/surface`; the surface tool block is deduped against the C0 block — a GATE-C1/C2 cleanup candidate.

**Binding split:** tools + skills are **hard** (C0 act-or-explain rule — invoke it or state why not); conventions are **advisory** (consider it). The `binding` field in the `/api/surface` response carries this label so every consumer can tell them apart without hard-coding class names.

**Causal acceptance metric (T13)** — `scripts/metric-surfacing.ts`, `npm run metric:surfacing`. The `logSuggestion` record in the hook gains optional `class`/`key`/`score`/`binding` fields (back-compatible, populated from the `/api/surface` response). The metric joins the suggestion log to `GET /api/observations/by-session` WITH TIMESTAMPS and counts a suggestion as accepted only when the matching tool/skill fires AFTER its surfacing timestamp in the same session — the **causal fix** vs C0's unordered co-occurrence (`scripts/metric-proactive-use.ts`, kept intact as the baseline). Reports per-class acceptance + overall precision-proxy + basis count. Server-down → suggestion-log-only stats. Honest limitation: acceptance ≠ relevance (true precision needs labels). **T35 (2026-07-26):** the operator-specific non-invokable tool keys (CLI scripts, scheduled automations, plugin-namespaced servers — structurally unmatchable via `mcp__` tool-name and excluded from the 'tool' rate) live in the untracked local file `~/.kopeng/non-invokable-tools.json` (object map `{key: rationale}`; `KOPENG_NON_INVOKABLE_TOOLS` overrides the path), merged over an EMPTY shipped default — personal keys stay out of the public cut (this closed a forbidden-token publish blocker where a personal project key had been inlined). Fail-soft: missing/malformed file → the metric still runs with the default.

**Trigger-rewrite proposer (T14)** — `scripts/propose-trigger-rewrites.ts`, `npm run propose:triggers`. Drafts reactive→observational ("use when you observe X") trigger rewrites for operator-owned skills as a reviewable before/after report (written to `docs/chief-of-staff/trigger-rewrite-proposals.md`, created on demand). Writes NO skill file — applying an accepted rewrite is operator-action (skills live in `~/.claude/`, operator-owned, out of repo).
