# Ops, Replay, and Live Stream Endpoints

> Extracted verbatim from CLAUDE.md (2026-09-07).

### Ops Endpoints

Read-only operational visibility surface backing the viz `ops` tab. Ten `GET /api/ops/*` endpoints return JSON snapshots (the count includes `scope-drift` and `scope-registry`, which arrived after the original eight); the viz polls them on a setInterval gated by the active tab (10s fast cadence for the light ones; 30s for the heavier on-demand decay/dup compute). The two heavy endpoints (`top-decaying`, `corpus-health`) are memoized in-process for 60s (keyed by limit/sample with `sample` quantized to 500-row buckets, in-flight promise dedup, failures never cached, expired keys swept on write + hard cap on map size) — repeated polls are ~2ms cache hits; at most one recompute per key per minute, so their *effective* refresh under the viz's 30s cadence is ≤60s.

- **`/api/ops/discovery-status`** — global watermark vs `MAX(observations.id)`, recent run count, the last 20 completed `discovery_runs` for a sparkline, and (T19) `last_observation_at` (`IObservationStore.getLastObservationAt`) backing the viz "senses" age light (green <1h / amber <24h / red beyond; a disabled feed reads red, never silent). Returns `{ enabled: false, ..., last_observation_at: null }` when observation ingestion is disabled.
- **`/api/ops/reasoner-status`** (T21) — read-only dream-reasoner liveness so an armed-but-dark provider can't be silent: `{ armed, provider, reachable, model, url, last_classify_at, error? }`. `armed` = `DREAM_REASONER_ENABLED`; `reachable` is a **fail-soft** probe of `${url}/api/tags` (down/slow/garbling ⇒ `reachable:false`, never a throw), null when disarmed; `last_classify_at` is an in-process stamp the live `LocalOllamaReasoner` sets on each successful classify (`ReasonerActivity`, `src/dreaming/reasoner/liveness.ts`). Built by `buildReasonerStatus` (closure in `server.ts`, wired through `AppContext.services.reasonerStatus`); degrades to a disarmed status when the dreaming stack isn't constructed. When armed the server also persists `operator_config.reasoner_provider = 'ollama'` (column-targeted read-merge-write — the `config` JSON blob is untouched) for display truth. Boot the provider with `scripts/ops/install-ollama-task.ps1` (at-boot S4U `ollama serve`, no time limit).
- **`/api/ops/last-promotion`** — most recent `promotion_runs` row + last 10 for history. Empty `{ last: null, recent: [] }` until the promotion pipeline runs after Tier-2 ships (the table is new; nothing logs to it pre-Tier-2).
- **`/api/ops/confidence-distribution`** — confidence histogram bucketed into the auto-discovery tiering tiers (`noted ≤ 0.55`, `pattern (0.55, 0.65]`, `actionable (0.65, 0.85]`, `confirmed > 0.85`), broken out by memory type and rolled up by tier.
- **`/api/ops/top-decaying?limit=N`** — top N memories by decay score ascending (most decayed first). Computes `computeDecayScores()` on-demand over all active memories (~0.15s on 4000 rows / PG; cached 60s). Polled on the slow cadence in the viz.
- **`/api/ops/cache-stats`** — dedup ratio (`memories_reinforced / (memories_created + memories_reinforced)`) plus aggregate totals over the last 100 completed discovery runs. Read-only derivation from existing `discovery_runs` rows — no separate instrumentation.
- **`/api/ops/dream-history?limit=N&offset=M`** — most-recent **completed** dream passes with per-pass change counts (proposed / auto_applied / accepted / rejected / pending + `by_change_class`), derived from each dream's stored `output_diff` resolution (falls back to the dream's own counters). Completed-only by design (mirrors `getLastCompletedDream` — a record of what dreaming *changed*, not a pass-failure log); failed passes are intentionally excluded. **Team-review #22:** audit-carrier rows (promotion decay / discovery maintenance) are INCLUDED and labeled `is_carrier: true` — they perform real archives, so this is their operator-facing record (they remain excluded from `getLastCompletedDream` and `listPendingDreams`, where the exclusion is load-bearing). The endpoint is memoized like the two heavy ones (60s, keyed by limit/offset) — `output_diff` re-parsing per poll wasn't free once Phase-2 provenance fattened diffs. Returns `{ enabled: false, dreams: [] }` when the dream store is absent. Backed by `IDreamStore.listRecentDreams`.
- **`/api/ops/corpus-health?sample=N`** — point-in-time corpus-quality snapshot: `active_memory_count`, `mean_confidence` (exact, full-corpus, undecayed — matches confidence-distribution), `contradiction_flagged_count` (exact), and the duplicate-pair scan (cosine ≥ `COSINE_DUPLICATE_THRESHOLD`) + `decayed_at_risk_count` (**Phase 4: `!isAnchored(m) && isDecayedAtRisk(m, now)` — the SAME shared archive-line predicate as promotion/dream/maintenance, with Hard-Anchored rows now EXCLUDED**, so the panel counts exactly what promotion would archive; the dream decay tier carries the same rows minus any decayed row that is also an exact-dup member — that row rides the exact_dup entry instead (assertion 4 of the composition suite pins the group membership and the decay-set delta; which member that entry KEEPS is `pickKeepTarget`'s highest-confidence/most-recent rule, and the entry applies only on operator accept while `auto_accept_exact_dup` ships OFF) (maintenance §2 is the documented R4-B dormancy-freeze subset — see the Maintenance section); panel == promotion set-equality is pinned by `tests/unit/decay-predicate-composition.test.ts`, and the count can read LOWER than pre-Phase-4 on the same corpus because anchored at-risk rows no longer inflate it. The sample rows carry `type` + `tags` since Phase 5 round 2, so the count runs the per-type half-life + structural floor; before that it silently ran the default 60d floorless curve and could disagree with what dreaming actually archives) computed over a **bounded sample** (default 2000 active rows ascending; `meta.sampled`/`note` flag undercounting on larger corpora — the O(n²) dup scan is the cost guard, same pattern as `top-decaying`). **Duplicate pairs carry an actionability breakdown** (`duplicate_pairs: { total, actionable, anchored, cross_scope, condition_linked }`, classified via `classifyDupPair` exported from `src/dreaming/pipeline.ts` — sharing the selector's predicate FUNCTIONS (`isAnchored`, condition-provenance, the alias closure) so the metric is kept in step with what dreaming does; honest scope: the selector never calls `classifyDupPair` itself — precedence is mirrored, not shared, with metric↔selector agreement pinned on the alias case by `tests/unit/pipeline-alias-scope.test.ts`): only `actionable` (same-scope, unanchored, non-provenance) pairs are dreaming's to collapse; `anchored` (Hard Anchor) and `cross_scope` (R6 promote-not-collapse) are by-design exempt. **The dreaming-health diagnostic is `actionable`, not the total** — `actionable > 0` while dreams propose nothing means the rotating window isn't co-windowing those pairs (R12 → whole-corpus mode); a large total with `actionable = 0` is the healthy steady state (verified live 2026-07-03: 134 total = 31 anchored + 103 cross-scope + 0 actionable, and dreaming's 20+ empty passes were CORRECT). `duplicate_pair_count` (= `total`) is kept for back-compat. The scan (~1.3s CPU on a 2000-row sample) yields to the event loop every 16 outer rows so a recompute never blocks the event loop in long stretches (~10ms slices between yields; the recall hook runs on a 3s budget), and the 60s memo means it runs at most once a minute. Backed by `IMemoryStore.getCorpusHealthStats` + `getCorpusHealthSample` (SQLite + Postgres). This is the metric behind the leaner-corpus claim — the CI-gated `npm run dream:effectiveness` harness asserts it end-to-end on a synthetic corpus (non-zero exit on failure); the live over-time half is *measured* by the T24 weekly series, not asserted by any gate — and the per-pass time-series source for the launch video. **Weekly snapshot (T24):** `npm run snapshot:corpus-health` appends this endpoint + confidence-distribution as one JSONL line to `~/.kopeng/metrics/corpus-health.jsonl`; scheduled via the Task Scheduler pair `scripts/ops/install-corpus-health-task.ps1` → `corpus-health-task.ps1` (weekly, S4U as the operator — never SYSTEM, the log lives under `~/.kopeng`). Runbook: `docs/ops/corpus-health-snapshot.md`.

- **`/api/ops/scope-drift`** (T43 Phase A, detector half) — the watch on scope-namespace drift. **Why it exists:** T46's write-time canonicalization is an EXACT-STRING lookup (`forward.get(scope) ?? scope`), so it only catches variants already in the operator's alias table; a brand-new casing/separator variant of a known entity (`client:Acme-Foods` when the table knows only `client:AcmeFoods`) still lands verbatim. T46 closed KNOWN drift — this closes the blind spot on NEW drift. Returns slug-clustered variants (`kind: 'casing'` = mechanically aliasable, `'cross_prefix'` = a `client:`/`project:` collision that is always an operator ruling, never auto-proposed) with the per-variant evidence that made the 2026-08-14 reconciliation cheap: **`by_type` breakdown** (in all seven cross-prefix calls the `project:` side was ~96% `discovery` and the `client:` side held zero — that settled every one on sight), active/archived split, and first/last write. **Two headline numbers, deliberately distinct:** `active_rows_adrift` (LIVE rows on un-aliased variants — the time-series metric; reads 0 on a reconciled corpus so any rise is new drift) and `clusters_actionable` (uncovered clusters holding live rows — "how many rulings do I owe?"). `clusters_uncovered` is the wider structural count and reads HIGHER, because archived rows stranded on an alias scope are a known, accepted migration residue (a driver's `residual 0` counts active rows only — 178 such rows survived the live run) that is reported per-variant but never counted as drift. Verified against the real corpus 2026-08-14: 14 uncovered / 7 actionable / 1211 adrift, which reconciled EXACTLY to the deferrals (1185 `project:Acme-platform-backup` + 22 Acme family + 3 path-shaped + 1 new `project:200+`) — counts are the real ones, scope names are redacted to synthetic stand-ins. Cost: one `GROUP BY (scope, type)` — no content scan, no O(n²) — so it rides the light 10s ops cadence, not the memoized heavy pair. The clustering (`slugifyScope`/`clusterScopes`) lives in `src/scopes/drift.ts` and is IMPORTED by `scripts/ops/propose-scope-aliases.ts` rather than duplicated — a drift detector with its own drifting definition of drift would be a self-defeating bug. Alias-table read is fail-open to `{}` (corrupt blob or no operator-config store ⇒ "nothing covered yet", never a 500 on an ops poll). Backed by `IMemoryStore.getScopeAggregates` (SQLite + Postgres, sharing the exported `foldScopeAggregates`). **T76 §5.1 widened the evidence:** `getScopeAggregates` also folds a `by_source` breakdown per scope (same shape as `by_type`; NULL source folds under `'unknown'`) so the panel can separate auto-discovery drift from operator-authored drift instead of inferring it through the type proxy. **Item 11 adds `anchored` per scope** — ACTIVE rows the Hard Anchor protects, i.e. exactly what an archive of that scope would refuse. It existed only as `refused_anchored` in an archive dry-run RESULT, which is the wrong order: it is an input to "junk or real work?", not a consequence of acting. Counted in SQL because the aggregate must stay one `GROUP BY`, which makes it the anchor contract in a second language — so the SQL lives beside `isAnchored` as **`ANCHORED_SQL_PREDICATE`** (`src/dreaming/scoring.ts`, the `ARCHIVED_SQL_PREDICATE` precedent) with one entry per dialect, and `tests/unit/anchored-aggregate.test.ts` pins SQL ≡ TS over a corpus exercising all three anchor spellings plus every trap the two dialects offer: `pinned: false`, whitespace JSON, malformed metadata, the word "pinned" inside unrelated content, and — the two that matter — **`{"pinned":1}` and `{"pinned":"true"}`**, neither of which `isAnchored` accepts. Those two are why the SQL is spelled the way it is. SQLite MUST use `json_type(...) = 'true'`, never `json_extract(...) = 1`, because json_extract maps JSON `true` and the integer 1 to the same SQL 1 (the trap the `legacy_anchor_count` query already documents — the first draft of this constant reintroduced the very spelling that comment exists to reject, and a test corpus without a numeric-pinned row made the equivalence pin vacuous). Postgres MUST use `metadata->'pinned' = 'true'::jsonb`, never `->>'pinned' = 'true'`, because `->>` unquotes and would match the JSON string `"true"`. Both are wrapped in COALESCE: `metadata` DEFAULTs to `'{}'`, so the raw comparison is three-valued and a future `WHERE NOT (…)` caller would otherwise get nothing back for nearly the whole corpus. SQLite additionally needs the lazily-evaluated `json_valid` CASE because `json_type` RAISES on malformed JSON, which would take the aggregate down for every scope over one bad row. Active-only by design (an archived row cannot be archived again). PG twin in the executed-SQL suite. `getScopeAggregates` also gained **`by_source_active`**, the ACTIVE-only companion to `by_source` (free — the group row already carries its own active count): mixing the all-rows `by_source` with the active-only `active` compares two populations, and on a scope with a large archived backlog that arithmetic reported *zero* operator-written rows while live ones sat there. The panel renders all of it as the **triage line at rest** — `N auto-discovery · M other-source · K anchored · idle Xd` on both row kinds. The archive framing (the warning colour and "an archive would refuse every row" when `anchored === active`) is gated to **ephemeral rows only**, because they are the only rows offering an archive: a cluster variant's actions are `merge_into` / `mark_distinct`, and the Hard Anchor constrains neither — an alias entry moves nothing and refuses nothing — so colouring every operator-confirmed variant was alarm noise on the decision the line exists to speed up. `other-source` is deliberately not called "human": `source` records the WRITE PATH, and only the auto-discovery bucket is machine-generated with certainty. Acknowledged exposure (team review T-L1): the endpoint is keyless like every ops endpoint and already lists the full scope inventory, so `by_source` widens what an unauthenticated caller learns per scope; the `127.0.0.1` bind default remains the real control, and admin-gating the endpoint is recorded as an option, not taken here. **T76 §5.3 adds the ruled-distinct release:** a `mark_distinct` ruling (see Scope Registry & Minting, above) excludes its scope from `clusters_uncovered`/`clusters_actionable` without hiding the cluster — `clusters_ruled_distinct` in `data.summary` counts these, each cluster carries a `ruled_distinct` flag (true iff every uncovered variant has been ruled distinct), and the `ephemeral` list gained the same two fields per entry (`aliased_to`, `ruled_distinct`) so the panel can hide the archive-ephemeral action once a scope's release path is settled. The ruled-distinct input is `DistinctRulings` (`src/scopes/drift.ts`) — a class with a PRIVATE constructor, buildable only from a registry snapshot or its own `EMPTY`, so no ad hoc set can forge it; the drift route reads it fail-OPEN to `EMPTY` on a registry outage, meaning drift over-reports rather than silently absorbing a broken read (the same safe-side posture as the alias-table fail-open). **Trend:** `npm run snapshot:corpus-health` folds `summary` into its weekly JSONL line as `scope_drift`, fetched BEST-EFFORT outside the main `Promise.all` so a 404 from an older server can never cost the operator their corpus-health line. **Panel shipped (T76 Task 9):** the viz `ops` tab renders this report — worst-first cluster cards with per-variant `by_type`/`by_source` evidence, a cross-prefix evidence-hint badge that never pre-selects (Ruling L-1), and the ephemeral list — driving three admin-keyed actions: approve-alias (`POST /api/admin/scopes/rule {action:'merge_into'}`, sequential per-variant calls that stop on first failure), mark-distinct (`{action:'mark_distinct'}`), and archive-ephemeral (dry-run → confirm, see Scope Registry & Minting, above). The viz proxy's `ADMIN_ROUTES` allowlist gained `/api/admin/scopes/rule` and `/api/admin/scopes/archive-ephemeral` so the admin key injects server-side for both.

All ops endpoints are public (no API key) — same threat model as `/api/stats`. They depend on `queries: IMemoryStore` (and `observationStore: IObservationStore?` where applicable) already available in the AppContext shape — no new service dependencies.


### Replay Endpoints

Read-only historical session playback surface backing the viz `replay` tab. Two `GET /api/observations/*` endpoints return JSON snapshots; the viz fetches once per session selection and advances through the event array client-side with a `setTimeout` loop — no SSE.

- **`/api/observations/sessions?limit=N`** — recent sessions ordered by `MIN(started_at) DESC`. Each row: `session_id`, `observation_count`, `started_at`, `ended_at` (`MAX(COALESCE(completed_at, started_at))`), `project_scopes[]`, `tool_names[]`. `limit` clamped to `[1, 200]`, defaults to 50. Backs the session-picker dropdown.
- **`/api/observations/by-session?session_id=…&limit=N`** — all observations for a given `session_id`, ordered by `id ASC`. `limit` clamped to `[1, 20000]`, defaults to 5000. Returns `400` if `session_id` is missing. Uses the `idx_obs_session_id` index already created by the v3 Postgres migration / observations-db schema.

Both endpoints are gated by `config.discovery.ingestionEnabled && observationStore` (same gate as the existing `/api/observations/*` routes) and are public — same threat model as `/api/observations/stream`.

**Replay UI playback model:**
- Inter-event delay = `min(real_delta_ms, 2000) / speed`. The 2000ms clamp keeps sparse sessions (30-min gaps) from sitting idle even at 16×.
- Scrub-bar jumps clear the pending timer, re-render the slice `[0..newIndex]` from scratch (no incremental un-append), and resume the timer if it was playing.
- Replay does NOT consume the SSE stream — pure historical playback. Coexists with `live` tab without double-rendering.
- Purged sessions: `observations.db` purge deletes rows older than N days. Sessions with no remaining observations simply won't appear in the picker; querying `by-session` on a purged session returns `{data: [], meta: {count: 0}}`. Tier-3.5 may hook the JSONL backfill importer (`scripts/import-jsonl.ts`, `npm run import:jsonl`) into a "rehydrate this session" button.

Store interface additions (`IObservationStore`): `getObservationsBySession(sessionId, limit?)`, `listSessions(limit?)`. Implemented for both SQLite (`ObservationQueries`) and Postgres (`PgObservationQueries`). Note SQLite uses `GROUP_CONCAT` for `project_scopes`/`tool_names` (comma-split in JS); Postgres uses `array_agg(DISTINCT ...)` which the pg driver returns as a native array.

`promotion_runs` is a new table in `memory.db` (SQLite migration v3, Postgres migration v4), mirroring the `discovery_runs` shape but tracking the promotion pipeline. `runPromotion()` in `src/promotion/promotion-engine.ts` writes a `running` row on start and updates it to `completed`/`failed` on exit with all counts. Failure to insert/update is logged but never throws — promotion always completes even if the table is missing.


### Live Observation Stream (SSE)

`GET /api/observations/stream` — Server-Sent Events feed of observation lifecycle events. Each ingest writes (single + batch POST, completion PATCH) fan out through an in-process `ObservationBus` (`src/services/observation-bus.ts`) to all connected subscribers.

- Event format: `id: <seq>\nevent: observation\ndata: <json>\n\n` where the JSON payload is `{ kind: 'started' | 'completed' | 'failed', seq, ts, observation }`.
- 15s comment-line heartbeats (`: hb <ts>`) keep idle connections open and report dropped-event counts.
- Backpressure policy: drop-on-slow-consumer per connection (checked via `res.writableNeedDrain`); cumulative drops are logged on disconnect.
- Auth: intentionally open even when `OBSERVATION_API_KEY` is set, so the local viz on port 8780 can subscribe without juggling headers. All payload content is post-scrub (same path as `/api/observations`).
- No on-connect backfill in v1 — clients see events as they happen.

The viz proxy (`scripts/viz-server.js`) detects SSE requests by URL prefix `/api/observations/stream` or `Accept: text/event-stream` and stream-pipes the upstream body via `Readable.fromWeb(...).pipe(res)` instead of buffering through `arrayBuffer()`.

The viz frontend has four tabs (`viz/index.html` + `viz/app.js`): `graph` (existing D3 bipartite render, default), `live` (real-time event list capped at 500 rows, color-coded by status, click a row to reveal input/output summaries), `ops` (Tier-2 operational visibility panels — see below), and `replay` (Tier-3 historical session playback — see Replay Endpoints below). The tab choice persists in `localStorage`. The `review` tab has three sections (round-2, 2026-07-03): a **dreaming-controls panel** (live operator-config toggles — nightly dreaming on/off via `dream_cadence`, both `auto_accept_*` flags, whole-corpus sweep off/monthly; the blob-resident whole-corpus key toggle sends only its own `config` key — the PATCH handler MERGES it server-side (T26) so rotation cursors in the same JSON blob are never clobbered — pinned by `tests/unit/operator-config-merge.test.ts`), the **pending-dreams review** (T8, unchanged), and a **history list of every completed pass** (`/api/ops/dream-history`) — clicking any pass opens its diff via `GET /api/dreams/:id/diff` (works for non-pending dreams; an empty pass reads "proposed no changes"), so a healthy-but-quiet corpus is visibly dreaming rather than looking dead.

**Viz performance model (2026-07-02 fix):** the graph tab pages the corpus via `GET /api/memories?limit=1000&fields=lite` (~5 round-trips instead of ~41; falls back to legacy `limit=100` paging on a 400 from a pre-`fields=lite` server). The D3 force layout ticks in `requestAnimationFrame` chunks instead of a blocking loop (a full synchronous re-render measured ~5.8s of frozen main thread on ~4400 nodes; now the worst task is <100ms and the graph settles visibly), with node positions cached across renders so filter/resize/theme/tab-return re-renders reuse the previous layout and only run a short low-alpha settle. Hover highlighting dims via one class on the container `<g>` plus a precomputed adjacency map (not per-node class writes), and tooltip tracking reads no layout on mousemove. `scripts/viz-server.js` gzips buffered JSON + static responses (`Accept-Encoding`-gated) and skips its embedding-strip reparse for `fields=lite` responses.

**Design-token re-skin (Phase 2, 2026-08-05):** the viz ships a verbatim copy of the operator's upstream design-system token file — re-copy it from upstream to pick up changes; never hand-edit it locally. `viz/styles.css` is the extension layer aliasing those tokens onto app-specific names; the alias block (and `data-theme`) live on `body`, not `:root`, so `cssVar()` reads `getComputedStyle(document.body)` — this is what fixed the historic cross-theme graph-palette drift where colors read `documentElement` and stuck on the void defaults. Four themes (`void`/`ops`/`amber`/`linen`) cycle via the header's icon toggle button. Graph node/edge selection is persistent across tab switches and re-renders (accent ring on the selected node + adjacency dim on the rest; clicking the empty canvas background clears it). The header's `P50` figure is the viz's own client-measured median over its last 50 `/api/*` fetches, not a server metric. Token primitives (the `*-pill`/`*-btn`/`*-check` classes) are composed onto existing badge/button/checkbox render sites across panels rather than replacing them outright.
